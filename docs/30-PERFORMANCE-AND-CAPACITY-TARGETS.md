# 30 — Performance & Capacity Targets

The old drafts required every phase to pass "API latency gates" without naming a
number. An unnamed gate is not a gate. These are the numbers, the corpus they are
measured against, and the machine they are measured on.

## Reference capacity

One workspace, deterministically generated by `tools/casual-task-seed`, committed
as a seed script so every measurement is comparable:

| Dimension | Reference | Design ceiling |
| --- | --- | --- |
| Tasks | 2,000,000 | 10,000,000 |
| Projects | 200 | 2,000 |
| Users | 500 | 10,000 |
| Tasks per project (p95) | 20,000 | 200,000 |
| Comments per task (p95) | 20 | 500 |
| Activity events | 20,000,000 | — |
| Concurrent SSE streams | 500 | 5,000 |
| Role assignments | 5,000 | 50,000 |
| Board column size (p95) | 200 | 2,000 |

**Reference** is what gates run against. **Ceiling** is where a design decision is
allowed to change — beyond it, a new ADR is expected rather than a heroic fix.

## Reference environment

Gates are meaningless without a named machine:

- **API/worker**: 4 vCPU, 8 GB.
- **PostgreSQL**: 8 vCPU, 32 GB, NVMe SSD.
- **Client**: mid-tier laptop (4-core, integrated graphics), broadband with
  Fast-3G-equivalent RTT.

Measurements from any other environment are recorded with the environment
attached and are not comparable to these gates.

## Throughput and async

| Metric | Target |
| --- | --- |
| Sustained write throughput | 500 mutations/s per API instance |
| Outbox dispatch lag (p95) | < 1 s |
| Search projection lag (p95) | < 2 s |
| Notification fan-out (p95) | < 5 s |
| SSE delivery after commit (p95) | < 500 ms |
| Automation trigger→action (p95) | < 10 s |

**Outbox lag is the health metric that matters most.** It is the first thing to
move when the database is under pressure, when a consumer is failing, or when a
worker has died — and it degrades user-visible liveness before latency does.

## Resource budgets

| Resource | Target |
| --- | --- |
| API idle RSS | < 50 MB |
| API RSS at reference load | < 512 MB |
| Worker RSS | < 256 MB |
| DB connections per API instance | 2 × vCPU + spare |
| Cold start | < 1 s |

The idle figure is a stated goal of the Rust decision (ADR-001) and matters
specifically to self-hosters running several services on one small box.

## Degradation policy

What is shed, and in what order, when the system is overloaded. Deciding this in
advance is the difference between graceful degradation and a random outage:

1. **Search** — the most expensive read. Sheds first, returns `503` with
   `Retry-After`.
2. **Analytics and report queries** — deferred.
3. **Automation** — queued; depth and rate limits already bound it
   ([36](36-AUTOMATION-RULES-DESIGN.md)).
4. **Notification fan-out** — queued; in-app records are still written.
5. **SSE** — new subscriptions refused; existing ones maintained.
6. **Never shed**: task read, task write, transition, authorization. If these
   fail, the product is down; everything above is a degraded but working product.

Shedding is explicit (`503` + `Retry-After`), never a silent timeout.

## Known scaling limits and their escape hatches

Each is a designed-in threshold with a pre-planned response, so hitting one is a
capacity task rather than a redesign:

| Limit | Threshold | Response |
| --- | --- | --- |
| `accessible_projects` array in queries | ~2,000 projects per actor | materialize `project_access` table ([26](26-SEARCH-INDEXING-AND-QUERY.md)) |
| Postgres full-text | p95 > 300 ms after tuning | external engine (ADR-014 tripwire) |
| Single-writer PostgreSQL | write saturation | read replicas for reads, then partition `task` by workspace |
| Outbox poll | > 10,000 events/s | shard by `workspace_id` hash across workers |
| SSE per instance | ~10,000 streams | horizontal scale + Redis fan-out |
| `activity_event` size | — | already partitioned; retention drops partitions (ADR-021) |
| Board rank length | > 32 chars | background compaction (ADR-013) |

## Anti-patterns, forbidden by gate

Each is a specific way this class of application dies, and each has an automated
check:

| Anti-pattern | Gate |
| --- | --- |
| Sequential scan on a tenant-scale table | `EXPLAIN` suite ([26](26-SEARCH-INDEXING-AND-QUERY.md)) |
| N+1 queries | query-count assertion per endpoint |
| Per-object permission resolution | resolution-count assertion (1 per list) |
| Offset pagination | lint: `OFFSET` is banned in application SQL |
| Unbounded result set | every query has `LIMIT`, asserted |
| Loading a whole project client-side | payload-size assertion per endpoint |
| Blocking I/O in an async handler | `tokio-console` check + lint |
| Unbounded channel or queue | lint on channel constructors |
| Plugin call inside a transaction | compile-time check ([19](19-WORKSPACE-SCAFFOLD-DESIGN.md)) |

## Measurement

- **`tools/casual-task-loadtest`** runs the scenarios above against a seeded
  reference corpus and emits a versioned JSON report.
- Baselines are committed to `benchmarks/` per named environment.
- CI fails on a **>10% regression** against the committed baseline, not on
  absolute numbers — absolute thresholds fail on CI noise and get disabled, which
  is worse than no gate.
- Full-suite runs are nightly; PR runs use a reduced corpus for signal.
- Production carries the same instrumentation, so a synthetic regression and a
  real one are described by the same metrics ([46](46-OBSERVABILITY-AND-OPERATIONS.md)).
